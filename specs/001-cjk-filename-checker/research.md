# Phase 0 Research: CJK Cross-Platform Filename & Folder Checker

**Feature**: `001-cjk-filename-checker` | **Date**: 2026-11-18

## 1. Unicode Normalization & CJK Anomaly Detection

- **Decision**: Use `icu_normalizer` (ICU4X 2.4 `ComposingNormalizerBorrowed::new_nfc()` / `DecomposingNormalizerBorrowed::new_nfd()` gated to Unicode `16.0.0` via a build-time `BMP_ASSIGNED_MASK` + `ASSIGNED_UNICODE_16_RANGES` slicing barrier generated from pinned UCD `16.0.0` `UnicodeData.txt`) combined with build-time generated static lookup tables derived from pinned UCD `16.0.0` `UnicodeData.txt`, `CJKRadicals.txt`, `confusables.txt` (UAX #39), `emoji-data.txt`, and `emoji-variation-sequences.txt` (UTS #51) for Kangxi Radicals (`U+2F00–U+2FD5`), CJK Radicals Supplement (`U+2E80–U+2EF3`), cross-script CJK/Kana confusables, and UTS #51 emoji context preservation. Per user decision (`1: B`), CJK Compatibility Ideographs with canonical decompositions (`U+F900–U+FAFF` and `U+2F800–U+2FA1F`, excluding the 12 UAX #15 non-decomposing unified ideographs) are classified as `AutoFixable` (converted to canonical CJK Unified Ideographs via NFC).
- **Rationale**:
  - Using `icu_normalizer = "2.4"` (required by `icu_collator 2.4.0` and `eframe 0.37.0 -> idna_adapter 1.2.2`) combined with the Unicode `16.0.0` `is_assigned_unicode_16()` slicing barrier (backed by the Unicode Normalization Stability Policy) and pinned Unicode `16.0.0` `UnicodeData.txt` canonical decomposition tables guarantees runtime NFC/NFD normalization strictly matches `ScanReport.unicode_version: "16.0.0"` and pinned `UnicodeData.txt` `16.0.0` without regressing 50,000-entry scan performance rather than relying solely on an older `unicode-normalization` Unicode 15.x table snapshot.
  - Standard `NFC` preserves Kangxi Radicals (`U+2F47` `⽇`) and does not convert them to CJK Unified Ideographs (`U+65E5` `日`).
  - Rather than subjective visual judgments, UCD `<compat>` decompositions determine track assignment deterministically: all Kangxi Radicals (`U+2F00–U+2FD5`) plus `U+2E9F` (`⺟→母`) and `U+2EF3` (`⻳→龟`) have `<compat>` mappings in `UnicodeData.txt` and are `AutoFixable`; the remaining `CJK Radicals Supplement` entries (`U+2E80–U+2EF2`) mapped only in `CJKRadicals.txt` are routed to `ManualReview` with candidate hints from `CJKRadicals.txt`.
  - Blanket `NFKC` converts Kangxi Radicals but also alters fullwidth ASCII, circled digits, and superscripts—causing unintended changes to valid filenames. Targeted mapping avoids NFKC side effects.
  - Under UAX #15, 12 characters in the CJK Compatibility Ideographs block (`U+FA0E`, `U+FA0F`, `U+FA11`, `U+FA13`, `U+FA14`, `U+FA1F`, `U+FA21`, `U+FA23`, `U+FA24`, `U+FA27`, `U+FA28`, `U+FA29`) are standalone Unified Ideographs with no canonical decomposition and MUST NOT be flagged as decomposing compatibility ideographs.
  - Under Unicode **UTS #51**, `U+FE0E`/`U+FE0F` (Text/Emoji Variation Selectors VS15/VS16) and `U+200D` (ZWJ) are mandatory structural components of valid emoji presentation and emoji ZWJ sequences (e.g., `❤️` = `U+2764 U+FE0F`, `👨‍👩‍👧`). Generating static UTS #51 sets from pinned `emoji-data.txt` and `emoji-variation-sequences.txt` preserves valid emoji filenames intact (`Edge Cases`, `SC-002`) while still flagging standalone or non-emoji occurrences attached to CJK/Hangul/ASCII characters as `VariationSelector` or `InvisibleZeroWidth`.
  - Under Unicode **UTS #39** (`confusables.txt`), uncontextualized whole-text matching causes massive false positives (`SC-002` failure) on standard ASCII alphanumerics (`0`/`O`, `1`/`l`/`I`) and legitimate Japanese Katakana words (e.g., `エラー.txt`, `カタログ.zip`, `コード.png` where `エ`, `ロ`, `カ`, `ー` belong to normal Kana tokens). Applying Context-Gated Confusable Detection restricts Katakana/Hanzi lookalike flags strictly to isolated Katakana characters embedded inside contiguous Han/Hangul tokens without adjacent Hiragana/Katakana, flags Cyrillic/Greek/mathematical homoglyphs when mixed with Latin or CJK/Hangul tokens, and exempts plain ASCII alphanumerics.
- **Alternatives Considered**:
  - Calling `NFKC` directly on all filenames: Rejected due to destructive side effects on fullwidth punctuation/alphanumerics.
  - Using OS-specific `NSString` / Win32 normalization APIs: Rejected because it breaks cross-platform determinism (SC-005).

## 2. Embedded OS-Independent Collation & Sort Profiles

- **Decision**: Use ICU4X 2.0+ (`icu_collator` with `CollatorPreferences` / `CollationNumericOrdering::True` and `BlobDataProvider` loading a checked-in, `icu4x-datagen`-generated `.postcard` blob for `ko`, `ja`, `zh`) for `MacOsKo`, `Japanese`, and `Chinese` profiles, alongside a distinct `WindowsKoKr` comparator (Unihan `kHangul` / KS X 1001 Hanja reading table + empirically verified Windows 11 `ko-KR` hierarchy `Whitespace -> Symbols/Punctuation (with Win32 StrCmpLogicalW Word-Sort secondary weighting for '-' and '\'') -> Numbers (0–9, natural numeric) -> Latin (A–Z) -> Hangul+Hanja -> Kana`) and a `LinuxCodePoint` (`C.UTF-8` scalar order) comparator, tagging each `SortDiscrepancy` with `DiscrepancyCause` (`EncodingAnomaly` vs `InherentPlatformCollation`).
- **Rationale**:
  - Synology NAS (DSM) and minimal Linux containers often lack `ko_KR`, `ja_JP`, and `zh_CN` OS locales. Embedding a compact `.postcard` collation blob via `include_bytes!` + `BlobDataProvider::try_new_from_static_blob` stored in `std::sync::LazyLock` yields `'static` `CollatorBorrowed<'static>` instances across macOS, Windows, Linux, and Synology NAS without external runtime dependencies or `compiled_data` binary bloat (FR-002, FR-008, SC-005).
  - Empirical screenshots from real Windows 11 Explorer (`ko-KR`: `A -> 가 -> 日` and `純 -> 애니포럼 -> 日 -> 화보집`) and macOS Finder (`ko`: `鹿 -> 鎖 -> 슈퍼 -> 유 -> 音 -> 柊 -> 春 -> 花 -> non -> あう`, matching CLDR `ko.xml` `[reorder Hang Hani]`) prove that `WindowsKoKr` places `Whitespace -> Symbols/Punctuation -> Numbers -> Latin -> Hangul+Hanja -> Kana` whereas `MacOsKo` places `Whitespace -> Symbols/Punctuation -> Numbers -> Hangul+Hanja -> Latin -> Kana`. Within `WindowsKoKr`, standard punctuation/brackets (`!`, `#`, `( )`, `[ ]`, `_`, `~`, `+`, `=`) sort in symbol order before digits while `-` and `'` follow Win32 `StrCmpLogicalW` Word-Sort secondary weighting (ignored in the primary pass unless strings otherwise tie).
  - No separate image/comic viewer sort profile is added; because mixed encodings (unnormalized NFD Hangul/Kana, Kangxi radicals, compatibility ideographs, invisible zero-width characters) are the primary root cause of unexpected jumps, normalizing filenames to UTF-8 NFC + canonical Unified Ideographs directly aligns cleaned entries as closely as possible with the `WindowsKoKr` visible sort order without trying to alter OS or third-party viewer sort engines.
  - Separating `DiscrepancyCause::EncodingAnomaly` (fixable via canonical normalization; reported in default scan findings and exit code `1`) from `DiscrepancyCause::InherentPlatformCollation` (unfixable OS script/locale rules; informational-only during profile comparison so clean mixed ASCII/Hangul folders never produce false-positive exit code `1`) keeps results actionable and preserves `SC-002`.
  - Generating the KS X 1001 (4,888 Hanja arranged in Korean reading order) / Unihan `kHangul` lookup table in `unicode_data.rs` gives `WindowsKoKr` deterministic Korean reading collation without external OS dependencies, while comparing contiguous ASCII digit runs as arbitrary-length character slices (overflow-free on >20-digit timestamps/hashes: compare stripped-leading-zero digit count, then lexicographical digits, then reverse leading-zero count so `"01" < "1"` matching Windows `StrCmpLogicalW`) guarantees faithful natural numeric ordering.
  - Using `CollatorBorrowed` with baked `ko`, `ja`, `zh` data, `O(N log N)` per-profile rank-vector sorting, and $O(N)$-bounded adjacent boundary inversion reporting keeps binary size compact and prevents $O(N^2)$ pair-materialization OOM on 50,000-file flat directories. Platform-native OS CI tests (`CompareStringEx`/`StrCmpLogicalW` on Windows; `localizedStandardCompare:` on macOS) validate accuracy against real OS behavior.
- **Alternatives Considered**:
  - Querying host OS `LC_COLLATE` / `CompareStringEx` / `localizedStandardCompare:`: Rejected as primary engine because results would vary by host OS and fail on headless NAS devices lacking all three CJK locales.

## 3. Non-UTF-8 Legacy Byte Detection & Decoding Hints

- **Decision**: Read directory entry names losslessly via `OsStr` (`std::os::unix::ffi::OsStrExt` `Vec<u8>` on Unix; `std::os::windows::ffi::OsStrExt::encode_wide` `Vec<u16>` on Windows), detect invalid UTF-8 bytes (Unix) or unpaired UTF-16 surrogates (Windows), and try lossless `encoding_rs` decodings across `CP949`/`EUC-KR`, `Shift_JIS`, `GB18030`, and `Big5` (ranked with `chardetng` score when available) so even short filenames always produce valid candidate hints in the Manual Review track (FR-006, FR-016).
- **Rationale**:
  - Linux ext4/btrfs and Synology NAS volumes can store arbitrary non-UTF-8 byte sequences from legacy FTP/ZIP/SMB clients. Standard `String` conversion would lossily replace bytes with `U+FFFD` or skip entries.
  - Because legacy 2-byte encodings (`CP949`, `Shift_JIS`, `GB18030`, `Big5`) expand by up to 1.5× when converted to 3-byte UTF-8 (potentially crossing the 255-byte `NAME_MAX` boundary on `ext4`/`btrfs`/`APFS`), decoded candidates and manual target edits are checked against the 255-byte `NAME_MAX` / 255-UTF-16-unit limit before rename to prevent `ENAMETOOLONG`.
  - Showing ranked candidate decodings as non-destructive hints prevents silent corruption when legacy encodings are ambiguous.
- **Alternatives Considered**:
  - Skipping non-UTF-8 entries or auto-converting via a single guessed encoding: Rejected because silent guessing risks permanent filename corruption.

## 4. Cross-Platform GUI & Static CLI Distribution

- **Decision**: Structure the repository as a 3-crate Cargo workspace:
  - `namechecker-core`: Pure Rust library with zero GUI/CLI dependencies.
  - `namechecker-cli`: `clap`-based CLI binary, statically linkable with `musl` for Synology NAS (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`) and native builds for macOS/Windows/Linux.
  - `namechecker-gui`: Pure Rust desktop GUI using `eframe`/`egui` + `egui_extras::TableBuilder` (virtual scrolling) + `rfd` (native folder dialog) + background worker thread (`std::thread::spawn` + `mpsc::channel` + `ctx.request_repaint()`) for non-blocking SMB/disk I/O and debounced `predicted_after_order` recalculation + `egui_kittest` for headless widget/AccessKit UI testing + Pan-CJK multi-font fallback stack (Korean + Japanese + Simplified/Traditional Chinese system fonts across macOS, Windows, and Linux).
- **Rationale**:
  - `eframe`/`egui` compiles to a single native executable with zero external WebView runtime dependencies (unlike Tauri, which requires WebView2 on Windows and WebKitGTK on Linux), directly satisfying FR-002. On Linux desktops, `eframe` and `rfd` dynamically use standard OS desktop libraries (`X11`/`Wayland`, `libxkbcommon`, `libGL`, `libgtk-3`), while `namechecker-cli` compiles statically with `musl` for zero-dependency execution on Synology NAS.
  - Because Windows `malgun.ttf` lacks full Japanese Kana/Kanji and Simplified Chinese glyph coverage, configuring a multi-font CJK fallback stack (`malgun.ttf` + `Yu Gothic`/`Meiryo` + `Microsoft YaHei` on Windows; `Apple SD Gothic Neo` + `Hiragino Sans` + `PingFang` on macOS; `Noto Sans CJK` on Linux) prevents missing-glyph tofu boxes (`☐`).
  - Offloading scan, rename, and debounced `predicted_after_order` recalculation to a background worker thread with `ctx.request_repaint()` prevents main-thread UI freezes on high-latency SMB network shares and 50,000-entry folders, while keeping `rfd::FileDialog::new().pick_folder()` on the main `eframe` UI thread to satisfy macOS AppKit main-thread and Windows COM STA requirements. Using `egui_kittest` enables deterministic headless UI verification under TDD.
  - Separating `namechecker-core` keeps the NAS CLI binary lightweight and allows 100% of detection, collation, collision, and safe-rename logic to be tested via `cargo test` in headless CI.
- **Alternatives Considered**:
  - Tauri (WebView-based): Rejected due to external WebView runtime dependencies and heavier cross-compilation footprint.
  - `iced`: Viable alternative, but `eframe`/`egui` has simpler CJK system-font fallback integration and lighter immediate-mode table rendering for large audit lists.

## 5. Filesystem Traversal, Symlink Safety & Safe Rename Protocol

- **Decision**:
  - Use a clean traversal abstraction backed by `std::fs::read_dir` in v1 (`max_depth = 1` immediate files and child folders of the target directory, extensible to `jwalk` for future hierarchical tree expansion) with `follow_links(false)` by default.
  - Implement a two-track rename engine: pre-flight collision check (verifying both unchanged on-disk siblings and intra-batch target `new_name` deduplication under NFC + case-folding) and 255-byte `NAME_MAX` / 255-UTF-16-unit length validation, symlink check (`symlink_metadata().file_type().is_symlink()`), atomic non-overwriting OS rename syscalls tried first (`renameat2` with `RENAME_NOREPLACE` on Linux, `renamex_np` with `RENAME_EXCL` on macOS, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows—converting absolute Windows paths to the Win32 verbatim namespace `\\?\C:\...` and `\\?\UNC\server\share\...` before syscalls so Win32 path normalization never strips trailing spaces/periods from `WindowsSmbHazard` entries or trips on `>260`-unit `MAX_PATH` paths—with guarded `symlink_metadata(dst) == NotFound` fallback prior to `std::fs::rename` ONLY when a network/SMB mount such as macOS `smbfs` returns `ENOTSUP` or Linux `cifs` returns `EINVAL`/`ENOSYS`), two-step temporary rename (`old` → `.__nc_tmp_<uuid>` → `new`) for case-only, NFD→NFC normalization-only, and canonical-equivalence changes on case- or normalization-insensitive filesystems (APFS/HFS+/NTFS/SMB) with bounded exponential-backoff retries (up to 5 retries / 6 total attempts: 25ms, 50ms, 100ms, 200ms, 400ms) on transient `ERROR_SHARING_VIOLATION` / `EBUSY` locks and post-rename on-disk NFD-forcing verification (`FilesystemForcedNfd` detection for legacy HFS+ volumes), and an append-only JSON rename audit log recording `file_id` alongside fallback metadata `(entry_type, byte_size, mtime_ns)` so `undo` stays reliable even when macOS `smbfs` or Linux `cifs` (`noserverino`) alters `st_dev` or synthetic `st_ino` across renames or remounts.
- **Rationale**:
  - Prevents data loss, collisions, and TOCTOU/symlink-escape hazards on shared NAS volumes while keeping v1 focused on the selected target directory (FR-012, FR-013, FR-014).
- **Alternatives Considered**:
  - Direct in-place `std::fs::rename` without pre-flight collision or depth sorting: Rejected due to silent overwrites on Windows/macOS/SMB and `ENOENT` failures when parent folders are renamed before children.
